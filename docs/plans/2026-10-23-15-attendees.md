# Attendees — implementation plan

> Tests are written first in every task. Nothing is committed or pushed until the owner says "ship it" (Task 8).

**Goal:** Members can say they are attending an event; Luma registrations are read in hourly and matched to members by
email; the event page shows a public count and a members-only list.

**Spec:** `docs/specs/2026-10-23-15-attendees.md` (approved).

**Architecture:** A closed table `event_registrations` plus `security definer` database functions are the only way in or
out. The hourly sync (already reading events from Luma) also reads each upcoming event's approved guest list and hands the
emails to `sync_luma_attendees`, which matches them to accounts without storing any email. The event page reads the count
through a cached call and the member's own status and the list through the member's session.

## Global constraints

- Production grants nothing automatically (memory `prod-supabase-no-default-grants`): every table and function gets
  explicit grants, and a database test proves them.
- Luma guest emails are never stored or logged. The Luma client stays read-only: `GET` only, a fixed list of paths.
- If a guest list is not read completely, that event's attendees are not touched.
- Visitors and members cannot read or write `event_registrations` and cannot read `events.luma_approved_count` directly.
- Pages read at request time (`Suspense` + `await connection()`), never during the build.
- Every action checks the session on the server; a logged-out caller is sent to `/login?next=<the event page>`.
- New text goes in `src/lib/copy.ts`. English. Names show as "Member" when empty.

### Task 1: Database (tests first)

- [ ] **Step 1: write `supabase/tests/attendees.test.sql`.** Setup as the superuser: members A, B, C (auth users with
  emails `a@x.test`, `b@x.test`, `c@x.test`; profiles come from the signup trigger, give A and B names and job titles), an admin D
  (role set by update), four events (`att-open` visible and upcoming with `luma_approved_count = 10`, `att-past` visible
  and ended, `att-hidden` hidden, `att-gone` removed_from_luma). Assertions, each scoped to these rows:
  1. visitors (`anon`): `select * from public.event_registrations` throws `42501`; same for a member; a member cannot
     `insert` or `update` or `delete` it directly (`42501`);
  2. a member and a visitor cannot `select luma_approved_count from public.events` (`42501`);
  3. visitors cannot run `my_attendance`, `event_attendees`, `set_attendance`, `set_list_visibility`, `sync_luma_attendees`,
     `admin_attendance` (`42501`); members cannot run `sync_luma_attendees` (`42501`);
  4. `set_attendance(att-open, true)` as A returns `registered`; a second call changes nothing; as A `my_attendance` shows
     `registered`, `self`, `show_in_list` true;
  5. `set_attendance(att-open, false)` as A makes it `cancelled`; marking true again makes it `registered` again;
  6. `set_attendance` raises for `att-past`, `att-hidden` and `att-gone` (a member cannot mark attendance there) and writes nothing;
  7. `event_attendance(att-open)` for a visitor returns `total = 10 + self rows` with `luma` and `self` null; for admin D
     returns the split; for a hidden event it returns no row to a visitor and a row to the admin;
  8. `event_attendees(att-open)`: a visitor throws `42501`; member B sees A when A is registered and listed, does not see
     A after `set_list_visibility(att-open, false)` as A, and the total in `event_attendance` still counts A;
  9. `sync_luma_attendees('evt-att-open', array['A@X.test', ' c@x.test ', 'stranger@nowhere.test'])` as `service_role`:
     matches A (different case) and C, ignores the stranger, returns `matched = 2`; A's earlier `self` row becomes
     `luma`; C gets a `luma` row; nothing stores the stranger's email (no table contains it); running it again changes nothing;
  10. a second call with only `c@x.test` cancels A's `luma` row (`cancelled = 1`) and keeps C; A's `show_in_list` setting
      survives a re-registration; an empty array cancels every `luma` row of that event; `set_attendance(..., false)` as C never
      cancels C's `luma` row; marking again after Luma cancelled makes a `self` row;
  11. the total never counts a member twice: a member who is `luma` is not added to the self count;
  12. `admin_attendance()` returns `(event_id, luma, self)` for every event to admin D and no rows to a member;
  13. deleting an account deletes its registrations (cascade), deleting an event deletes its registrations;
  14. production-like grants: `has_function_privilege('anon', ..., 'execute')` is false for every function above except
      `event_attendance`, `authenticated` can execute the member functions and not `sync_luma_attendees`, `service_role` can
      execute `sync_luma_attendees`.
  Use `events.test.sql` and `admin_events.test.sql` as the pattern for roles and `request.jwt.claims`.
