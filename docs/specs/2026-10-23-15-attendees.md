# Attendees — "I'm attending", counts, list, Luma registrations

Issue #15. Phase 4 of `2026-10-22-82startup-platform-design.md`. Where this document and the platform design differ,
this document wins for Phase 4.

## Scope

In:
- A member presses **I'm attending** on an event (and presses it again to cancel).
- Luma registrations are read in hourly and matched to members by email.
- The event page shows a public **attendee count**, and a members-only **attendee list**.
- A member can remove themselves from the list, per event.
- Admins see the count split into Luma and self-reported.

Out (later): Luma webhooks (see below), notifications, check-in, exporting attendees, ticket details, waitlist and
pending-approval views, attendee data on cards or the home page.

## Decisions (owner, 2026-10-23)

- **Luma registrations arrive by hourly read only.** The hourly job that already syncs events also reads each event's
  guest list. No webhook now: no new public address, no signature check, nothing for the owner to register in Luma. A
  registration can take up to an hour to show. A webhook can be added later on the same tables. Luma documents its
  webhook signature (headers `Webhook-Id`, `Webhook-Timestamp`, `Webhook-Signature` = `t=<time>,v1=<hex>`, HMAC-SHA256
  over `<time>.<raw body>` with the `whsec_` secret as given, constant-time compare, reject stale timestamps, dedupe by
  `Webhook-Id`), so that later step is well defined.
- **The list shows people automatically, and each member can leave it.** Members who registered on Luma with the same
  email as their account, and members who pressed **I'm attending**, appear in the members-only list. Each of them has a
  per-event switch "Show me in the attendee list". Hiding oneself removes the name from the list but not from the count.

## Data model

New table **`event_registrations`**, one row per event and member (unique pair):
`event_id` → `events`, `member_id` → `profiles`, `status` (`registered` | `cancelled`), `source` (`luma` | `self`),
`show_in_list` (boolean, default true), `created_at`, `updated_at`. Both foreign keys delete the row with their parent.
The table is closed: no direct read or write for visitors or members. Everything goes through the functions below.

New column **`events.luma_approved_count`** (integer, default 0): how many people Luma says are going (the event's
`guest_counts.approved.guests`). It is filled by the sync and includes people who are not members.

**Luma guest emails are never stored.** The sync passes them to a database function that matches them to members and
keeps only the member link.

## Counting and the one-row rule

- **Total shown to everyone** = `luma_approved_count` + the number of `source = self`, `status = registered` rows. A
  member who is on Luma has a `source = luma` row, which is already inside the Luma count, so nobody is counted twice.
- A member who pressed **I'm attending** and later appears in Luma's approved list: the same row becomes
  `source = luma`. If Luma later no longer lists them as approved, the row becomes `cancelled`, and they may press the
  button again (which makes a `self` row).
- A `source = self` row that is cancelled by the member stays as `cancelled` (history is kept; nothing is deleted).
- **Admins** see two numbers: the Luma count and the self-reported count. Everyone else sees one number.

## Database functions (all `security definer`, explicit grants)

| Function | Who may run it | What it does |
|---|---|---|
| `event_attendance(event_id)` | visitors and members | Returns `total`; returns `luma` and `self` only to an admin. Only for events the caller may see (published and visible; admins see all). |
| `event_attendees(event_id)` | members and admins | Returns the list: member id, name, job title, company, for `registered` rows with `show_in_list`. Not for visitors. |
| `my_attendance(event_id)` | members | Returns the caller's own row: status, source, show_in_list (or nothing). |
| `set_attendance(event_id, attending)` | members | Marks or cancels the caller as attending. Only for events that are published, visible and not ended. A row from Luma is never changed by this: the member cancels on Luma. |
| `set_list_visibility(event_id, show)` | members | Sets the caller's `show_in_list` for that event. |
| `sync_luma_attendees(luma_event_id, emails)` | the sync only (`service_role`) | Matches `emails` (case-insensitively) to account emails, creates or updates `luma` rows as `registered`, turns members' earlier `self` rows into `luma`, and cancels `luma` rows whose member is not in the list. |

`admin_attendance()` (admins only) returns the Luma and self counts for every event in one call, for the admin list.
The event page reads the event's database id (`events.id`), which is already a public column.

Production does not grant new objects automatically, so every function has its own `grant execute` and a test checks it.
Visitors and members cannot read or write `event_registrations` directly, and cannot read `luma_approved_count`
directly (it is public through `event_attendance` only).

## Luma sync changes

- The read-only Luma client gets one more `GET`: the event's guest list (`/v1/events/guests/list`, filtered to
  `approval_status=approved`, following the cursor). It is added to the allowed paths and still sends nothing but `GET`.
- For each event that has not ended, the sync reads the event details (it already does) to get
  `guest_counts.approved.guests` and stores it as `luma_approved_count`, then reads the approved guest list and calls
  `sync_luma_attendees` with the emails. Events that have ended are left as they were.
- If reading the guest list fails or does not finish, that event's attendees are **not touched** (nothing is cancelled),
  the error is counted and recorded on the event, and the sync goes on with the next event.
- The sync result gains counts of matched members; **Sync now** shows them.

## The event page

- Under the date and place: **N attending** (the total; hidden when it is 0).
- Next to **Get tickets**, a note: "Register on Luma with the same email as your account to be counted automatically."
- Logged in, event not ended: a button **I'm attending** / **Cancel attending**. If the member is registered through Luma,
  the button is replaced by "You're registered on Luma". A checkbox **Show me in the attendee list** appears whenever the
  member is attending.
- Logged out: "Sign in to say you're attending" linking to `/login?next=` this page.
- Members and admins see **Who's attending**: names with job title and company, soonest-registered order is not needed;
  alphabetical by name. Visitors do not see the list or any name.
- The admin list (`/admin/events`) shows `Luma: X · Self: Y` for each event.
- An empty name shows as "Member".

## Caching

The page's event data stays cached as today. The count is read through its own cached call tagged per event and expired
by the actions that change it (`updateTag`), so a member sees their own change at once. The member's own status and the
attendee list depend on who is logged in and are read at request time, never cached.

## Testing

Tests are written first.
- **Database:** visitors and members cannot read or write `event_registrations`, cannot read `luma_approved_count`
  directly, and visitors cannot call the member functions. `set_attendance`: marks, cancels, only for visible and
  not-ended events, refuses a hidden or ended event, never alters a `luma` row. `sync_luma_attendees`: case-insensitive
  match, unmatched emails ignored and not stored anywhere, self row turns into luma, a luma row whose member left the list
  is cancelled, a second run changes nothing, an empty list cancels the luma rows (the sync must only call it after a
  complete read). `event_attendance`: total equals Luma count plus self rows, a luma row is not counted twice, only admins
  get the split, a hidden event gives nothing to non-admins. `event_attendees`: only `registered` and `show_in_list` rows,
  not for visitors. The explicit grants hold when the default privileges are taken away.
- **Unit:** the guest-list read (paging, `GET` only, allowed path), the sync with a fake Luma and a fake store (counts,
  the failure rules above, nothing touched when the guest read fails, events that ended are skipped), form parsing for the
  new actions, the existing sync and cron tests still pass.
- **Browser QA (local):** as a visitor, a member and an admin: count, button, cancel, list visibility switch, the
  Luma-registered state (seeded), the sign-in prompt, ended event, 375px width.
- **Live read-only check:** one guest-list read against the production calendar to confirm the response shape (names and
  types only, no emails printed).

## Release

Merge; the owner runs `supabase db push --linked`; press **Sync now** on `/admin/events` once; on production check an
event page as the owner (count, button, list, the switch) and that a logged-out visitor sees only the count. No new
environment variable.
